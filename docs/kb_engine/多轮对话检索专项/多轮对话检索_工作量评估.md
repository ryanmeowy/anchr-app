## 逐模块评估

### 模块 1：会话管理（8.1）—— 🟡 中等（3~4 天）

**从零开始。** 当前没有任何 conversation 模型或持久化。

| 工作项 | 工时 |
|--------|------|
| `ConversationSession` + `ConversationTurn` 领域模型 | 0.5 天 |
| Redis 持久化 `ConversationSessionRepository`（参考 `SearchSessionManager` 模式） | 1 天 |
| `ConversationService`：创建/查询/追加 turn | 1 天 |
| REST 端点：`POST /api/conversations`、`GET /api/conversations/{id}`、`POST /api/conversations/{id}/messages`、`GET /api/conversations/{id}/messages` | 0.5 天 |
| 测试 | 0.5 天 |

> **3~4 天**

Redis 足够满足 MVP 阶段需求（单用户、会话量小）。如果未来需要持久化或查询历史，再迁到 DB。

---

### 模块 2：Query Rewrite（8.2）—— 🟡 中等（3~5 天）

**核心新逻辑。** 底层 LLM 能力已有（`AliyunGenManager`），但需要新建 rewrite 服务层和 prompt 工程。

| 工作项 | 工时 |
|--------|------|
| 新建 `QueryRewriteService`：组装上下文 + 调 LLM → 改写 query | 1 天 |
| Prompt 模板设计 + 调优（最近 3 轮上下文、实体提取、意图识别、模态偏好） | 1.5 天 |
| 新建 `SearchContentPort.generateText(prompt)` 或专用 `TextGenPort` | 0.5 天 |
| Fallback 策略（LLM 不可用时原样返回 user query） | 0.5 天 |
| `RewriteResult` DTO（originalQuery / rewrittenQuery / entities / modalities / confidence） | 0.5 天 |
| 测试 | 0.5 天 |

> **3~5 天**

风险点：prompt 调优可能需要多轮迭代，实际耗时取决于 LLM 对 rewrite 任务的表现。

---

### 模块 3：对话式检索编排（8.3）—— 🟢 低投入（1~2 天）

**大量复用。** PRD 明确要求"不新造搜索系统，复用现有 RRF / rerank / explain / metrics"。

| 工作项 | 工时 |
|--------|------|
| 新建 `ConversationRetrievalOrchestrator`：接收 rewritten query → 调 `UnifiedSearchService` → 返回 topK candidates | 1 天 |
| 上下文感知检索选项（从会话中提取 modality preference、主题约束） | 0.5 天 |
| 测试 | 0.5 天 |

> **1~2 天**

`UnifiedSearchService.search(KbSearchQueryDTO)` 已封装完整检索链路，编排层几乎就是一次直接调用 + 结果裁剪。

---

### 模块 4：回答生成（8.4）—— 🔴 高投入（4~6 天）

**全新模块，且是体验核心。** 需要 prompt 工程 + grounding 策略 + 安全兜底。

| 工作项 | 工时 |
|--------|------|
| 新建 `AnswerGenerationService`：取 top 3~5 grounding segments → 拼 prompt → 调 LLM → 结构化解析 | 1.5 天 |
| Prompt 模板：含检索证据注入、回答风格约束、引用标记要求 | 1.5 天 |
| "无证据"兜底：当 topK score 过低或结果为空时，返回"未找到足够内容"而非编造 | 0.5 天 |
| 回答结构化输出：摘要 + 要点列表 + 图文补充 + 参考来源 | 0.5 天 |
| `AnswerResult` DTO（answerText / citations / evidenceSegments / confidence） | 0.5 天 |
| 回答失败降级（LLM 不可用时返回检索结果原样） | 0.5 天 |
| 测试 | 0.5 天 |

> **4~6 天**

风险点：grounding 质量取决于检索结果和 LLM 遵循指令的能力。幻觉控制需要 prompt 迭代。

---

### 模块 5：引用与溯源（8.5）—— 🟢 低投入（1~2 天）

| 测试 | 0.5 天 |

## 与 Phase 3 的对比

| 维度 | Phase 3（工程增强） | 多轮对话检索专项 |
|------|--------------------|--------------------|
| 工作量 | 29~45 天 | 22~35 天 |
| 难度 | 广而杂（重建/实验/指标/版本 4 条线） | 深而新（LLM prompt 工程 + grounding） |
| 对 LLM 依赖 | 无 | 高（rewrite、answer、follow-ups 全依赖） |
| 复用现有能力 | 中（检索参数已有，重建/实验从零） | 高（检索链路完全复用） |
| 主要风险 | 工程量大、持久化改造 | prompt 质量、幻觉控制、延迟叠加 |

## 建议推进顺序

1. **先做会话管理 + 检索编排（3~6 天）** —— 最基础、最无风险。会话 CRUD + 调现有 `UnifiedSearchService`，不做 rewrite 和 answer，先让"多轮提问 → 多轮搜索结果"跑通。

2. **再做 Query Rewrite（3~5 天）** —— prompt 设计是关键，建议先用 20 条典型追问迭代 2~3 轮 prompt 版本。

3. **再做回答生成（4~6 天）** —— 整个专项中不确定性最高的模块。grounding 效果取决于 prompt 工程，建议先跑通 MVP（简单拼接 + 生成），再优化结构化和引用标记。

4. **最后做推荐追问 + UI（3~5 天）** —— P1 内容，可以在回答生成稳定后再加。

5. **监控指标穿插进行** —— 每个模块做完顺手加 MeterRegistry 埋点，不要集中到最后补。
